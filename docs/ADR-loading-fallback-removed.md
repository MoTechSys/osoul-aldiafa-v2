# لماذا حُذف src/app/loading.tsx

**القرار**: حُذف ملف `src/app/loading.tsx` في فرع `release/p0-consolidated`.

**السبب** — الملف كان يُبطل جوهر إصلاح P0-2 بينما كل الحرّاس خضراء:

في App Router، وجود `loading.tsx` يلفّ محتوى الصفحة تلقائيًا في `Suspense`.
ولأن الشجرة تحتوي مكوّنًا بـ`ssr: false` (`FloatingWhatsApp` داخل
`ClientLayout`) فإن React يُخرج الحدّ في حالة **معلَّقة** ويكتب في HTML الخادم
هيكل الانتظار لا المحتوى:

```html
<main id="main-content"><!--$?--><template id="B:1"></template>
  <div ...>جاري التحميل...</div>
```

المحتوى الحقيقي يوجد لاحقًا في الحمولة ويُبدَّل عبر `$RC("B:1","S:1")` — أي
**بعد تنفيذ JavaScript**. النتيجة: زائر بلا JS (أو زاحف لا ينفّذها كاملًا)
يرى «جاري التحميل...» مكان الصفحة كلها.

هذا هو بالضبط العيب الذي جاء P0-2 ليُصلحه، وكان سيمرّ صامتًا: `typecheck`
و`lint` و`vitest` و`build` و`check:seo` و`check:assets` كلها خضراء، لأن فاحص
السيو يقرأ الوسوم والنصوص الموجودة في الحمولة. الذي كشفه هو اختبار
`tests/e2e/no-js-content.spec.ts` بمتصفح حقيقي وJavaScript معطّل — ثلاثة من
اختباراته فشلت، وكان نصّ الصفحة المُستلَم فعليًا «جاري التحميل...».

**قياس قبل/بعد** (بناء الفرع نفسه):
- قبل: `<main>` يبدأ بحدّ Suspense معلَّق + شاشة التحميل؛ 3 اختبارات no-js فاشلة.
- بعد: `<main>` يبدأ بمحتوى الصفحة؛ 16/16 اختبار e2e أخضر، صفر عنصر مخفي في SSR.

**البديل إن أُريدت شاشة تحميل لاحقًا**: أعِد `loading.tsx` فقط بعد إزالة
`ssr: false` من `ClientLayout` (أو نقل `FloatingWhatsApp` خارج الشجرة
المُعلَّقة)، وأعِد تشغيل `tests/e2e/no-js-content.spec.ts` كشرط قبول. الشاشة
ليست ضرورية أصلًا لصفحات ثابتة (SSG) تُقدَّم مبنيّة مسبقًا.
